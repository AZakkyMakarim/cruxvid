# Spike cruxvid-b2t.2: FFmpeg, caption ASS, encoder (Windows half)

Status: Windows half done. Android half NOT attempted (building/running Android is out of scope for this run); see "Needs device check".

Reproduce: `python spikes/b2t-2/run.py` (stdlib only; needs `ffmpeg`/`ffprobe` on PATH). Outputs go to `spikes/b2t-2/out/` (git-ignored). Takes about 5 minutes (fixture + `-preset medium` encode).

## 1. Installed FFmpeg capabilities

Binary: gyan.dev `8.1.1-essentials_build` (GPL, static). Probed with `-filters/-encoders/-muxers/-demuxers/-protocols`.

| Need | Present | Note |
|---|---|---|
| libass (`ass`, `subtitles` filters) | yes | `--enable-libass` |
| freetype / fribidi / harfbuzz / fontconfig | yes | `drawtext` also available |
| libx264 | yes | GPL, matches ADR 0001 |
| HLS | yes | `hls` muxer + demuxer, `https`/`crypto` protocols |
| AAC | yes | native `aac` |
| h264_mediacodec | no | Windows build; Android-only, so not testable here |

The essentials build already covers everything the Windows sidecar needs. It is 96.8 MiB (101,457,920 bytes) for `ffmpeg.exe`; `ffprobe.exe` is 96.6 MiB (each is statically linked with every codec).

What the "custom build" must add or change:
- Windows: nothing functional. Custom build is only for size: `--disable-everything` then enable only `libx264`, `aac`, `ass`/`scale`/`crop`/`fps`/`overlay`/`amix`... filters, `mov`/`mp4`/`hls` mux/demux, `file`/`https` protocols, `libass`, `freetype`, `fribidi`, `harfbuzz`. Expect a large reduction vs 96.8 MiB; the exact figure needs an actual build (not done, out of scope).
- Android (cross-compile, arm64-v8a): `--enable-mediacodec --enable-jni --enable-libass --enable-libfreetype --enable-libfribidi --enable-libharfbuzz`, no `libx264` (ADR 0001: hardware `h264_mediacodec`), no fontconfig (not available on Android; use `fontsdir`, see section 4). Network/HLS/https needs an SSL lib (mbedtls or openssl) if FFmpeg must fetch HLS itself; if yt-dlp downloads files first, not needed.

## 2. Burn-in pipeline

ASS template: `shared/ass/caption.ass.tmpl` (header + style, placeholders `{{FONT}}`, `{{SIZE}}`, `{{OUTLINE}}`, `{{MARGIN_V}}`). PlayRes 1080x1920, so font sizes are in output pixels. The spike script appends events:
- One `Dialogue` per word, lasting exactly that word's duration (0.4 s in the fixture).
- Each event shows the current 4-word line; the active word is wrapped in `{\c&H00E6FF&}WORD{\c}` (yellow), the rest use the style's white. Two rules learned: only upper-case the word text, never the tags (`.upper()` on the whole line turns `\c` into the invalid `\C` and silently loses the highlight; the first run hit exactly this); and keep size/margins such that 4 upper-case words fit in 1080 px (96 pt overflowed, 68 pt fits).
- `\k` karaoke tags were not used: with one event per word, colour override is simpler and gives the same visual result.

Encode (one pass, source landscape fixture to 9:16 crop):

```
ffmpeg -i fixture.mp4 -vf "scale=-2:1920,crop=1080:1920,fps=30,ass=captions.ass:fontsdir=/Windows/Fonts" \
  -fps_mode cfr -c:v libx264 -profile:v high -pix_fmt yuv420p -preset medium \
  -b:v 8M -maxrate 12M -bufsize 16M -g 60 -c:a aac -b:a 128k -ar 48000 -movflags +faststart export.mp4
```

Fixture: 90 s, 1280x720 30 fps, `testsrc2` desaturated + temporal noise (noise keeps the bitrate near 8 Mbps), 440 Hz sine, generated by the script (not committed).

## 3. Results (Windows)

ffprobe assertions (all asserted in the script and passing):
- 1080x1920, `h264`, profile `High`, `yuv420p`
- `r_frame_rate == avg_frame_rate == 30/1`, and all video packet pts gaps equal 1/30 s (true CFR)
- video bitrate 8.02 Mbps (asserted 6-10), audio AAC 128 kbps, duration about 90 s
- `moov` atom before `mdat` (faststart)

Captions burned, verified pixel-wise and visually:
- Frame at 10.2 s vs the same fixture frame without captions: mean abs diff in caption band (y 1300-1700) 27.0 vs 16.1 in a control band (y 100-500; the control is non-zero because of lossy re-encode of noisy content). Asserted `caption > control + 10`.
- Highlight-yellow pixels that are not yellow in the caption-free frame: centroid x moves 426 (t=10.2, word "FROM") to 615 (t=10.6, next word), asserted `> 50` px apart. Frame saved to `spikes/b2t-2/out/frame_10.2.png` and inspected: white outlined text with the active word in yellow.

Binary size: `ffmpeg.exe` 96.8 MiB (101,457,920 bytes); output `export.mp4` 87.4 MiB for 90 s.

Notes: encode time with `-preset medium` for 90 s of noisy 1080x1920 is about 3 min on this machine (CPU x264); Export of 60-120 s Clips will be similar, so the real app should show progress and may prefer `-preset veryfast` or h264_nvenc/qsv as an option. Not measured further.

## 4. Android font fallback: proposal only (not tested)

- Android has no fontconfig, and libass in an Android FFmpeg build needs an explicit font source. Proposal: ship 1-2 fonts in the app (Latin + a broad-coverage fallback such as Noto Sans / Noto Sans Symbols) and pass them with `ass=...:fontsdir=<app files dir>/fonts`; point libass at `/system/fonts` as a second fontsdir only if one directory can be given (the filter takes one `fontsdir`, so copy or symlink the needed system fonts into the app dir at first run).
- Caption style stores a font name; at render time check the font is in the app fonts dir, else rewrite `Fontname` in the generated ASS to the bundled fallback before FFmpeg runs. This makes "missing font" deterministic and avoids tofu boxes (libass uses its default fallback font only if one is found).
- Use the same bundled fonts on Windows (`fontsdir` = app resources) so both platforms render the same glyphs from the shared template.
- Needs device validation: libass font matching behaviour on Android, glyph coverage for non-Latin Transcript languages (the Edge case in the ticket).
